## Overview

TaskFlow is a polyglot repository with two independent dependency-management surfaces:

- **Frontend** (`Apps/Web`): Node.js/TypeScript, managed by **pnpm** with a lockfile and workspace overrides.
- **Backend** (`Services`): ASP.NET Core (.NET 10), managed via MSBuild `PackageReference` elements in `.csproj` files. No NuGet config or global packages are present.

There is no shared monorepo tool tying the two sides together — each language ecosystem manages its own dependencies independently.

## Frontend: pnpm

### Manifest & Lockfile

- Declaration file: `Apps/Web/package.json`
- Lockfile: `Apps/Web/pnpm-lock.yaml` (generated by pnpm)
- Workspace config: `Apps/Web/pnpm-workspace.yaml`
- Enforced package manager: `"packageManager": "pnpm@12.21.0"` in `package.json`, which pins the exact pnpm version used for installs.

### Versioning strategy

- Most runtime dependencies use caret ranges (`^x.y.z`) allowing patch/minor upgrades within the declared major.
- A few core packages are pinned to exact versions: `next` (`16.4.6`), `react` (`19.3.1`), `react-dom` (`19.3.1`), `@types/react` (`19.3.0`), `@types/react-dom` (`19.3.0`).
- Dev-only tooling (`oxlint`, `oxfmt`, `tailwindcss`, `typescript`, `@tailwindcss/turbopack`) uses caret ranges.

### Overrides

`Apps/Web/pnpm-workspace.yaml` declares:

```yaml
allowBuilds:
  sharp: false
  unrs-resolver: false
overrides:
  '@types/react': 19.3.0
  '@types/react-dom': 19.3.0
```

This forces all transitive dependencies to resolve `@types/react` and `@types/react-dom` to the exact versions matching React 19, preventing type mismatches from third-party packages that still depend on older `@types/*`. It also disables native builds for `sharp` and `unrs-resolver` (likely to speed up CI / avoid platform-specific build failures).

### Scripts

The frontend exposes standard Next.js scripts plus lint/format commands backed by Oxc (`oxlint`, `oxfmt`). There is no custom install/update script; updates are expected to be done through pnpm CLI commands.

## Backend: .NET PackageReference

### Project structure

Four projects under `Services/`, each with its own `.csproj`:

| Project | Purpose | External packages |
|---|---|---|
| `Services.Domain` | Pure domain entities/value objects/enums | None |
| `Services.Application` | Application services + DI registration | `Microsoft.Extensions.DependencyInjection` 10.0.12 |
| `Services.Infrastructure` | EF Core + PostgreSQL persistence, Identity, JWT | `Microsoft.AspNetCore.Authentication.JwtBearer` 10.0.12, `Microsoft.AspNetCore.Identity.EntityFrameworkCore` 10.0.12, `Microsoft.EntityFrameworkCore` 10.0.12, `Microsoft.EntityFrameworkCore.Tools` 10.0.12, `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.3 |
| `Services.Api` | Web API entrypoint | `Microsoft.AspNetCore.Authentication.JwtBearer` 10.0.12, `Microsoft.AspNetCore.OpenApi` 10.0.12, `Microsoft.EntityFrameworkCore.Design` 10.0.12, `Scalar.AspNetCore` 2.18.0 |

All projects target `net10.0` and enable `<Nullable>enable</Nullable>` and `<ImplicitUsings>enable</ImplicitUsings>`.

### Versioning strategy

- All Microsoft.* packages are aligned at **10.0.12** (matching .NET 10 SDK).
- Third-party packages have their own versioning: `Npgsql.EntityFrameworkCore.PostgreSQL` at `10.0.3`, `Scalar.AspNetCore` at `2.18.0`.
- Build/design-time tools (`Microsoft.EntityFrameworkCore.Design`, `Microsoft.EntityFrameworkCore.Tools`) are marked with `<PrivateAssets>all</PrivateAssets>` so they do not leak into downstream project references.

### Internal project references

Dependencies between layers are expressed as `ProjectReference` elements (not NuGet packages):

```
Services.Api → Services.Application + Services.Infrastructure
Services.Infrastructure → Services.Application + Services.Domain
Services.Application → Services.Domain
Services.Domain → (none)
```

This enforces a strict layered architecture where only adjacent layers reference each other.

### NuGet source configuration

No `NuGet.config` exists anywhere in the repository. The backend relies on the default NuGet.org feed and any user-level/global NuGet sources. There is no private registry, no `GOPRIVATE` equivalent, and no vendored packages.

## Cross-cutting conventions

1. **No vendoring**: Neither side vendors third-party code. Node modules live under `node_modules/` (gitignored) and NuGet packages are restored from feeds.
2. **Lockfiles committed**: `Apps/Web/pnpm-lock.yaml` is tracked in git, ensuring reproducible frontend installs across environments.
3. **Exact pnpm version**: The `packageManager` field in `package.json` pins pnpm to `12.21.0`, so anyone running `pnpm install` gets the same resolver behavior.
4. **Type definitions pinned**: Both the `package.json` and `pnpm-workspace.yaml` pin `@types/react` and `@types/react-dom` to `19.3.0` to match React 19.
5. **Design-time packages isolated**: .NET design/build tools use `<PrivateAssets>all</PrivateAssets>` to keep them out of transitive package graphs.
6. **No CI automation visible**: There is no workflow file in this snapshot that automates dependency updates (e.g., Dependabot, Renovate); updates appear to be manual.
